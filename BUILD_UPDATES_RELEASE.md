# Build versions and follower updates

Creators open **Project settings → Manage builds**, or the build-management link in My projects. They can save a named build with 10–300 characters of release notes, then select the active version once the project is published. Saving an unfinished build does not announce it. Activating a different version, including reverting to an older version, records a distinct release event; selecting the current version again does nothing. This is release metadata, not a deployment service: the builder deploys the external project separately.

The current heart action is Save; there is no separate likes table. Members who saved before the release receive an in-app update with the version, notes and a link to its public release history, unless they disable saved-project updates. Notifications are materialized through the existing notification bell polling and dashboard visits. Offline members receive their eligible updates when they return; no email or push is sent. Release events have no seven-day cutoff. Read state survives repeated polls.

Version state and release events are stored atomically in the existing private `site_settings` table, keyed by project ID. A revision comparison rejects conflicting edits. No migration is required. Project owners with verified email can mutate their versions; published-only public reads exclude unannounced builds. The current limits are 100 builds and 1,000 activations per project, with an explicit error at the limit. Export includes build history and account erasure removes the stored build state.
